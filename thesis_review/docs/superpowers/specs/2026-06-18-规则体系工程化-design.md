# 规则体系工程化设计

日期：2026-06-18
状态：代码已实现，Word 样本待手动放置

## 1. 背景

当前项目已经具备 Word 提取、规则检查、批注写回和 Web 上传下载的基础框架。目录 C 类规则已经验证了从真实 `.docx` 样本到规则命中的完整链路。

但当前规则体系仍偏向开发验证阶段：

- 规则编号 `C001/C002/C003` 粒度偏粗，一条编号包含多个独立检查点。
- `docs/rule` 更像人工笔记和样本路径索引，不适合作为多人维护的规则资产库。
- Word 批注文案、期望值等信息分散在 Python 代码中。
- 测试样本与“错在哪里、应该命中哪些规则”没有结构化绑定。
- 后续规则会持续增加，如果不先固定规则资产格式，后续维护成本会快速上升。

本设计目标是建立一套清晰、可扩展、可迭代、适合多人维护的规则体系。

## 2. 目标

1. 使用小写英文全词作为规则编号，不使用缩写。
2. 每个规则编号只代表一个原子检查点。
3. 使用 `rule.yml` 集中管理规则编号、标题、说明、严重程度、状态、批注文案和期望值。
4. 使用 `case.yml` 集中管理 Word 样本、样本说明、错误说明和预期命中规则。
5. Python 规则代码只负责定位、判断、生成实际值和位置，不再硬编码批注文案和期望值。
6. 支持多人维护：规则新增、修改、废弃、样本补充都有稳定流程。

## 3. 非目标

本次设计不做以下事情：

- 不实现新的规则代码。
- 不立即迁移所有历史样本。
- 不设计复杂规则 DSL。
- 不要求非开发人员直接修改 Python 代码。
- 不要求一个 Python 类对应一个业务规则编号。
- 不在 `rule.yml` 中保留 `object`、`category`、`scope` 字段。

## 4. 规则编号设计

### 4.1 编号格式

规则编号统一使用：

```text
<module>-<subject>-<number>
```

要求：

- 全部小写。
- 使用英文全词。
- 单词之间使用 `-`。
- 不使用缩写，例如不用 `toc`、`ref`、`ack`、`app`。
- `number` 使用三位数字，从 `001` 开始。
- 一个编号只对应一个原子检查点。

示例：

```text
table-of-contents-title-001
table-of-contents-title-002
table-of-contents-entry-001
main-text-heading-001
references-item-001
thanks-title-001
appendix-title-001
```

### 4.2 模块名

第一轮固定以下模块名：

| module | 中文名 | 说明 |
|---|---|---|
| `cover` | 封面 | 封面区域规则 |
| `abstract` | 摘要 | 中文摘要、英文摘要、关键词 |
| `table-of-contents` | 目录 | 目录标题、目录条目 |
| `main-text` | 正文 | 正文标题、正文段落、图表等 |
| `references` | 参考文献 | 参考文献标题、条目格式 |
| `thanks` | 致谢 | 致谢标题和正文 |
| `appendix` | 附录 | 附录标题、附录内容 |
| `global` | 全文通用 | 页边距、纸张、页码等跨模块规则 |

模块名可以新增，但不能随意重命名。若确实需要重命名，必须在 spec 中记录迁移决策，并废弃旧编号，不复用旧编号。

### 4.3 原子规则原则

一条规则必须满足：

```text
一个 rule id = 一个检查对象 + 一个判断条件 + 一条批注文案
```

不再使用粗粒度编号：

```text
C001 目录标题格式
```

应拆成：

```text
table-of-contents-title-001  目录标题文本应为“目    录”
table-of-contents-title-002  目录标题字号应为三号
table-of-contents-title-003  目录标题中文字体应为黑体
table-of-contents-title-004  目录标题应居中
table-of-contents-title-005  目录标题行距应为 1.5 倍
table-of-contents-title-006  目录标题后必须且只能空一行
```

目录条目规则可拆成：

```text
table-of-contents-entry-001  一级目录编号与标题之间应空 2 个普通空格
table-of-contents-entry-002  二级目录编号与标题之间应空 1 个普通空格
table-of-contents-entry-003  三级目录编号与标题之间应空 1 个普通空格
table-of-contents-entry-004  目录条目中文字体应为宋体
table-of-contents-entry-005  目录条目数字和西文字体应为 Times New Roman
table-of-contents-entry-006  目录条目字号应为小四
table-of-contents-entry-007  目录条目行距应为 1.5 倍
table-of-contents-entry-008  目录条目不应加粗
```

## 6. rule.yml 设计

### 6.1 字段示例

```yaml
module: table-of-contents
module_name: 目录

rules:
  - id: table-of-contents-title-006
    title: 目录标题后空行
    severity: error
    status: active
    description: 检查“目    录”标题段落之后是否正好有一个空段落。
    message: 目录标题后必须且只能空一行
    expected: 1 个空段落
```

### 6.2 字段含义与用途

| 字段 | 必填 | 用途 |
|---|---|---|
| `module` | 是 | 所属模块的英文名，给代码和路径校验使用。它必须和模块目录名一致，例如 `thesis_review/docs/rules/table-of-contents/rule.yml` 中必须写 `module: table-of-contents`。 |
| `module_name` | 是 | 模块中文名，给维护者、规则列表、后台页面和文档展示使用。代码逻辑不依赖中文名做判断。 |
| `rules` | 是 | 当前模块下的规则列表。一个模块可以包含多条原子规则。 |
| `id` | 是 | 规则唯一编号，贯穿代码、测试、报告和 Word 批注。一旦规则发布，不允许改名或复用。 |
| `title` | 是 | 规则短标题，用于规则列表和管理页面展示。它应简短，例如“目录标题后空行”，不承担完整错误说明。 |
| `severity` | 是 | 严重程度，用于区分错误、警告和提示。允许值为 `error`、`warning`、`info`。报告和前端可以按此字段分组或使用不同样式。 |
| `status` | 是 | 规则状态，用于控制规则生命周期。允许值为 `draft`、`active`、`deprecated`。只有 `active` 默认参与正式审核；废弃规则保留编号但不再启用。 |
| `description` | 是 | 给维护者看的详细说明，用于解释这条规则到底检查什么、边界是什么。它主要服务规则评审、代码实现和后续维护，不一定直接展示给学生。 |
| `message` | 是 | 规则命中时展示给用户的问题文案，用于 Word 批注和审核报告。它回答“哪里不符合规范”。 |
| `expected` | 是 | 规范要求的期望值，用于 Word 批注和审核报告。它回答“正确应该是什么”。 |

运行时只加载 `rule.yml`。规则代码命中某个 `id` 后，只需要提供实际值 `actual` 和定位 `location`；`IssueFactory` 根据 `id` 从 `rule.yml` 中读取 `severity`、`message`、`expected`，再统一生成 `Issue`。

### 6.3 不保留的字段

`rule.yml` 不保留以下字段：

| 字段 | 原因 |
|---|---|
| `object` | 检查对象已经体现在规则编号和标题中 |
| `category` | 当前阶段不需要按格式/结构分类统计，避免概念过多 |
| `scope` | 检查范围由模块目录、代码和分区层共同决定 |

### 6.4 message 与 expected 的区别

`message` 是告诉用户“哪里不符合规范”：

```yaml
message: 目录标题后必须且只能空一行
```

`expected` 是告诉用户“正确应该是什么”：

```yaml
expected: 1 个空段落
```

代码运行时生成 `actual`，不写入 `rule.yml`。

最终批注可组合为：

```text
[table-of-contents-title-006] 目录标题后必须且只能空一行
期望：1 个空段落
实际：0 个空段落
```

## 7. case.yml 设计

### 7.1 字段示例

```yaml
cases:
  - id: table-of-contents-title-006-missing-blank
    file: samples/table-of-contents-title-006-missing-blank.docx
    description: 目录标题后没有空段落。
    error_description: “目    录”标题后面直接接目录条目，没有按规范空一行。
    expected_rule_ids:
      - table-of-contents-title-006

  - id: table-of-contents-clean
    file: samples/table-of-contents-clean.docx
    description: 目录规则无误样本。
    error_description: 无错误，用于验证目录规则不误报。
    expected_rule_ids: []
```

### 7.2 字段含义

| 字段 | 必填 | 含义 |
|---|---|---|
| `cases` | 是 | 样本列表 |
| `id` | 是 | 样本唯一编号 |
| `file` | 是 | Word 样本路径，相对当前模块目录 |
| `description` | 是 | 样本整体说明 |
| `error_description` | 是 | 文本描述这个样本错在哪里；无误样本写“无错误，用于验证不误报” |
| `expected_rule_ids` | 是 | 该样本应该命中的规则编号列表 |

`error_description` 使用英文 key、中文 value。这样代码读取稳定，维护者也能直接看懂内容。

## 8. 代码结构设计

### 8.1 规则元数据加载

新增规则目录加载层：

```text
thesis_review/src/thesis_review/rules/catalog/
├── loader.py
└── models.py
```

职责：

- 读取 `thesis_review/docs/rules/**/rule.yml`。
- 校验字段完整性。
- 校验所有 `id` 全局唯一。
- 校验 `module` 和目录名一致。
- 校验 `severity` 和 `status` 只使用允许值。
- 提供按 `rule_id` 查询规则元数据的接口。

### 8.2 Issue 创建

新增统一 Issue 创建层：

```text
thesis_review/src/thesis_review/rules/issue_factory.py
```

`IssueFactory` 的核心职责是把规则元数据和规则代码的检测结果合成为 `Issue`。它负责公共字段，规则代码只负责判断结果。

职责分工：

| 位置 | 负责内容 |
|---|---|
| `rule.yml` | 规则编号、严重程度、批注文案、期望值 |
| 规则代码 | 是否违规、实际值 `actual`、定位 `location` |
| `IssueFactory` | 根据 `rule_id` 查询元数据，并统一生成 `Issue` |

规则代码不再直接写：

```python
Issue(
    rule_id="table-of-contents-title-006",
    severity="error",
    message="目录标题后必须且只能空一行",
    expected="1 个空段落",
    actual="0 个空段落",
    location=location,
    ...
)
```

而是使用：

```python
issue_factory.create(
    rule_id="table-of-contents-title-006",
    actual="0 个空段落",
    location=location,
)
```

`IssueFactory` 从 catalog 中读取 `severity`、`message`、`expected`，规则代码只传 `actual` 和 `location`。最终生成的 `Issue` 等价于：

```python
Issue(
    rule_id="table-of-contents-title-006",
    severity="error",
    message="目录标题后必须且只能空一行",
    expected="1 个空段落",
    actual="0 个空段落",
    location=location,
)
```

最小接口建议：

```python
class IssueFactory:
    def __init__(self, catalog: RuleCatalog):
        self.catalog = catalog

    def create(
        self,
        rule_id: str,
        actual: str | None,
        location: Location,
    ) -> Issue:
        ...
```

如果规则代码传入的 `rule_id` 不存在，`IssueFactory` 必须直接报错，例如：

```text
Unknown rule id: table-of-contents-title-999
```

不能静默生成 Issue，也不能自动降级为普通错误。这样能在测试阶段发现规则代码和 `rule.yml` 不一致。

使用 `IssueFactory` 的好处：

- 批注文案和期望值集中在 `rule.yml`，不散落在 Python 代码中。
- 所有 Issue 的生成格式一致。
- 后续如果 `Issue` 增加 `module_name`、`rule_title`、`help_text` 等字段，只需要扩展 catalog 和 `IssueFactory`。
- 规则代码更短，只保留判断逻辑、实际值和定位。

### 8.3 规则检查器

当前 `Rule` 协议假设一个类有一个 `rule_id`。重构后不再强制“一类一编号”。

建议改为：

```python
class RuleChecker(Protocol):
    checker_id: str
    rule_ids: tuple[str, ...]

    def check(self, context: RuleContext) -> list[Issue]:
        ...
```

一个检查器可以覆盖同一对象的一组原子规则，例如：

```text
TableOfContentsTitleChecker
  - table-of-contents-title-001
  - table-of-contents-title-002
  - table-of-contents-title-003
  - table-of-contents-title-004
  - table-of-contents-title-005
  - table-of-contents-title-006
```

这样业务规则编号保持原子，Python 类数量也不会失控。

### 8.4 RuleContext

新增规则上下文：

```python
class RuleContext:
    document: DocumentModel
    sections: dict[str, SectionRange]
    catalog: RuleCatalog
    issue_factory: IssueFactory
```

`RuleContext` 是规则运行时共享上下文。它不做规则判断，只集中保存每个检查器都会用到的公共数据和工具，避免每条规则重复计算、重复加载、重复创建。

字段用途：

| 字段 | 用途 |
|---|---|
| `document` | 当前审核对象，即 extractor 从 Word 中提取出的 `DocumentModel`。规则读取段落、run、字体、字号、行距等信息都从这里开始。 |
| `sections` | 文档分区结果，例如 `cover`、`abstract`、`table-of-contents`、`main-text`、`references`。它在 pipeline 中只计算一次，所有检查器共享同一份分区结果。 |
| `catalog` | 从 `rule.yml` 加载出的规则元数据目录，包含 rule id、严重程度、文案、期望值、状态等。检查器通常不直接拼文案，而是通过它或 `IssueFactory` 获取规则元数据。 |
| `issue_factory` | 统一创建 `Issue` 的工具。检查器命中问题时只传 `rule_id`、`actual` 和 `location`，由它补齐 `severity`、`message`、`expected`。 |

使用 `RuleContext` 的原因：

- `sections` 只在 pipeline 中计算一次，避免每条规则重复调用 `detect_sections(document)`。
- 所有规则使用同一份分区结果，避免不同规则对模块边界的理解不一致。
- 规则检查器只保留判断逻辑，不负责加载规则元数据或拼接 Issue 文案。
- 后续如果增加规则开关、学校模板、日志、用户选项等共享信息，可以放入 `RuleContext`，不需要修改每个检查器的函数签名。
- 单元测试可以构造一个最小 `RuleContext` 来测试检查器，不必每次运行完整 pipeline。

### 8.5 完整执行流程

审核从 Word 输入到批注输出的流程：

```text
开始审核
|
|-- 打开 docx
|
|-- extractor.extract()
|   |
|   |-- 读取段落、run、表格、图片、字体、字号、行距等
|   |
|   '-- 得到 DocumentModel
|
|-- load_rule_catalog()
|   |
|   |-- 读取 thesis_review/docs/rules/**/rule.yml
|   |-- 校验 rule_id 是否唯一
|   |-- 校验 severity/status 是否合法
|   |
|   '-- 得到 RuleCatalog
|
|-- detect_sections(document)
|   |
|   |-- 尝试识别 cover
|   |-- 尝试识别 abstract
|   |-- 尝试识别 table-of-contents
|   |-- 尝试识别 main-text
|   |-- 尝试识别 references
|   |-- 尝试识别 thanks
|   |-- 尝试识别 appendix
|   |
|   '-- 得到 sections
|
|-- 创建 RuleContext
|   |
|   |-- document = DocumentModel
|   |-- sections = detect_sections 的结果
|   |-- catalog = RuleCatalog
|   '-- issue_factory = IssueFactory(catalog)
|
|-- registry 返回所有检查器
|
|-- 逐个执行 checker.check(context)
|   |
|   |-- 检查器先判断自己依赖的模块是否存在
|   |-- 模块不存在时按模块 gate 处理
|   |-- 模块存在时只读取该模块 SectionRange 内的数据
|   |
|   '-- 命中规则后通过 IssueFactory 创建 Issue
|
|-- 汇总 Issues
|
'-- annotator 写入 Word 批注
```

### 8.6 模块 gate

结构缺失时不全局停止后续规则，而是只停止依赖该模块的规则：

- 缺少目录：目录条目规则跳过，目录标题缺失规则仍报错。
- 缺少正文：正文规则跳过，不影响目录和参考文献规则。
- 缺少参考文献：参考文献条目规则跳过，不影响正文规则。

模块未匹配到时：

```text
检查器开始
|
|-- 需要模块 table-of-contents
|
|-- context.sections 中没有 table-of-contents
|   |
|   |-- 如果这是“模块存在性 / 标题存在性检查器”
|   |   |
|   |   '-- 报缺失问题
|   |       rule_id = table-of-contents-title-001
|   |       actual = 未找到目录
|   |
|   '-- 如果这是依赖目录内容的检查器
|       |
|       '-- 直接跳过，不报错
|
'-- 返回 issues
```

模块匹配到时：

```text
检查器开始
|
|-- 需要模块 table-of-contents
|
|-- context.sections 中存在 table-of-contents
|   |
|   |-- 取出 SectionRange
|   |
|   |-- 只遍历该范围：
|   |   paragraphs_in_range(context.document, table_of_contents_section)
|   |
|   |-- 对范围内段落逐条检查
|   |
|   |-- 命中错误时：
|   |   issue_factory.create(
|   |       rule_id="table-of-contents-title-006",
|   |       actual="0 个空段落",
|   |       location=location,
|   |   )
|   |
|   '-- IssueFactory 从 rule.yml 补齐 severity/message/expected
|
'-- 返回 issues
```

目录模块示例：

```text
DocumentModel
|
|-- detect_sections 找到：
|   table-of-contents:
|     start = 10
|     end = 15
|
|-- 目录标题检查器
|   |
|   |-- 只看 flow_index 10 附近的目录标题和紧邻空段落
|   |-- 检查标题文本、字体、字号、居中、行距、标题后空行
|   '-- 生成 table-of-contents-title-* issues
|
|-- 目录条目检查器
|   |
|   |-- 只看 flow_index 10 到 15 范围内的目录条目
|   |-- 跳过空段落
|   |-- 跳过目录标题
|   |-- 检查目录条目空格、字体、字号、行距、不加粗
|   '-- 生成 table-of-contents-entry-* issues
|
'-- 不检查 flow_index 15 之后的正文
```

硬约束：

1. 模块规则不得直接全篇遍历 `document.blocks` 做业务匹配。
2. 模块规则必须从 `context.sections` 获取自己的模块范围。
3. 模块规则必须使用 `blocks_in_range(...)` 或 `paragraphs_in_range(...)` 遍历模块内数据。
4. 未匹配到模块时，只允许模块存在性或标题存在性检查器报缺失问题。
5. 依赖模块内容的检查器在模块缺失时必须跳过，避免重复报错。
6. 目录规则不得把正文中的 `第一章...` 当作目录条目；是否属于目录必须由 `table-of-contents` 分区决定。

## 10. 维护规则

多人维护时必须遵守：

1. `rule_id` 一旦合入，不允许改名或复用。
2. 不再使用的规则标记为 `deprecated`，不删除编号。
3. 新规则先以 `draft` 状态提交，完成代码和测试后改为 `active`。
4. 每条 `active` 规则必须至少有一个测试覆盖。
5. 每个 `case.yml` 中的 `expected_rule_ids` 必须都能在 `rule.yml` 中找到。
6. 每个 Word 样本必须有 `description` 和 `error_description`。
7. 批注文案只能来自 `rule.yml`，不能散落在规则代码中。
8. 规则代码只能负责判断逻辑、实际值和定位。
9. 若规范解释发生变化，必须同时更新 `description`、`message`、`expected` 和样本预期。

## 13. 决策总结

- 正式规则编号使用小写英文全词，不使用 `A/B/C` 字母编号。
- 规则编号必须是原子检查点。
- 正式规则资产目录使用 `thesis_review/docs/rules/`。
- 每个模块使用 `rule.yml` 和 `case.yml`。
- `rule.yml` 不包含 `object`、`category`、`scope`。
- `case.yml` 必须包含 `error_description`，文本说明样本错在哪里。
- 批注文案和期望值集中放在 `rule.yml`。
- Python 规则代码只保留判断逻辑、实际值和定位。
