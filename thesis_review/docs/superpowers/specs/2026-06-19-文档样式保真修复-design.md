# 文档样式保真修复设计

日期：2026-06-19
状态：设计已确认，待实现【已修复】

## 1. 背景

当前审核系统使用 LibreOffice/UNO 读取 Word 文档、定位问题、写入红色底纹和批注，再另存为 `marked.docx`。这个方案能复用 UNO 的排版解析和批注写入能力，但 UNO 另存 DOCX 时会重写部分 OOXML 资产，已经观察到两类样式保真问题：

1. 字体主题和字体表被 LibreOffice 改写后，输出文档中的正文中文字体可能从输入的宋体等字体显示为黑体。
2. 输入样本中存在隐藏或兼容态的绘图对象时，UNO 另存会把 Word 的兼容结构重写成可见 DrawingML 对象，例如 `table-of-contents-entry-first-level-spacing.docx` 中原本带有 `组合 150` 箭头组，输出后在第七页右侧显露。

这两个问题都不是规则检测逻辑新增的内容，也不是批注文本本身造成的；根因是 UNO 对 DOCX 包结构的再序列化会改变 Word 原始资产。后续需要把“审核写入”和“样式保真修复”拆成两个明确阶段：UNO 负责写批注和底纹，OOXML 后处理负责恢复或约束不应被 UNO 改写的文档资产。

## 2. 目标

1. 继续使用 UNO API 完成文档读取、定位、批注和红色底纹写入。
2. 在 UNO 保存后，对输出 DOCX 做包级 OOXML 后处理，尽量保持输入文档的样式资产不被 LibreOffice 改写。
3. 保证 `issues == []` 的文档也走同一条 UNO 保存和 OOXML 后处理流程，不做直接复制。
4. 恢复输入文档的字体相关资产，避免中文主题字体、字体表、嵌入字体被 UNO 改写。
5. 对规则样本文档中的隐藏/残留绘图对象建立检测与治理机制，防止 UNO 另存后把非审核内容显露到输出文档。
6. 用 CLI 端到端测试覆盖 `docs/rules/<module>/samples/*.docx`，验证输出 `marked.docx` 的样式资产保真。

## 3. 非目标

- 不改为纯 OOXML 写批注。当前阶段仍以 UNO 为标注写入实现。
- 不尝试完全阻止 LibreOffice 对所有 DOCX XML 的重排和格式化。
- 不恢复整个 `word/styles.xml`，避免 LibreOffice 改写 styleId 或段落/运行属性后与原 styles 不一致。
- 不把样本文档复制到 `tests/fixtures/`；样本仍以 `docs/rules/*/samples/` 为唯一来源。
- 不把所有文档中的绘图对象一刀切删除；只处理明确属于样本污染或不应出现在审核输出中的对象。
- 不改变规则命中逻辑、规则编号、`issues.json` 输出语义。

## 4. 根因分析

### 4.1 字体变更

DOCX 的中文字体显示不仅由 `document.xml` 中的 run 属性决定，还依赖以下包级资产：

- `word/theme/theme1.xml`
- `word/fontTable.xml`
- `word/_rels/fontTable.xml.rels`
- `word/fonts/*`

UNO 保存时会重写这些资产，导致中文主题字体映射和字体表发生变化。即使正文 run 没有显式改成黑体，Word/WPS 打开输出文件时也可能按新的主题字体解析，表现为正文字体变化。

### 4.2 箭头显露

对 `table-of-contents-entry-first-level-spacing.docx` 和用户输出文件的 OOXML 对比显示：

- 输入文件本身包含 `name="组合 150"` 的 DrawingML 组合图形。
- 该组合图形内有红色、橙色、绿色箭头连接线。
- 输入文件还包含 WMF、OLE、VML fallback、`mc:AlternateContent` 等兼容结构。
- 仅用 UNO 打开输入并 `storeToURL` 另存，即使不写任何 issue、不调用字体资产恢复，也会在输出中保留并显露该组合图形。

因此箭头不是审核系统新画的，而是输入样本中的残留对象被 UNO 另存后显露。

## 5. 总体方案

审核输出分为三个阶段：

```text
input.docx
  -> UNO 读取和规则检测
  -> UNO 写批注/红底纹并另存 marked.docx
  -> OOXML 后处理恢复或治理样式资产
  -> issues.json + marked.docx
```

### 5.1 UNO 标注阶段

`adapters/uno/annotator.py` 继续作为唯一写批注和红色底纹的位置。

要求：

- 对每个 `Issue` 按既有 `Location` 定位并写入标注。
- 定位失败只记录 warning，不影响其他 issue。
- `issues` 为空时仍打开输入、保存输出，再进入 OOXML 后处理阶段。

### 5.2 OOXML 样式保真阶段

新增或扩展 `adapters/ooxml/` 包，承载所有 DOCX 包级修复逻辑。

建议模块边界：

```text
src/thesis_review/adapters/ooxml/
  __init__.py
  font_assets.py
  drawing_assets.py
  postprocess.py
```

职责：

| 模块 | 职责 |
|---|---|
| `font_assets.py` | 从输入 DOCX 恢复字体主题、字体表、字体关系和嵌入字体。 |
| `drawing_assets.py` | 检测和处理样本文档中的残留绘图对象。 |
| `postprocess.py` | 编排所有 OOXML 后处理步骤，供 UNO annotator 调用。 |

`annotator.py` 不应直接散落多个修复函数调用，最终应统一调用类似：

```python
postprocess_marked_docx(input_docx, output_docx)
```

## 6. 字体资产恢复设计

### 6.1 恢复范围

从输入 DOCX 原样恢复以下资产到输出 DOCX：

```text
word/theme/theme1.xml
word/fontTable.xml
word/_rels/fontTable.xml.rels
word/fonts/*
```

恢复规则：

1. 如果输入和输出都存在同名字体资产，以输入为准。
2. 如果输出存在 `word/fonts/*` 但输入不存在，删除输出中的 stale font 文件。
3. 如果输入存在某个字体资产而输出不存在，追加写入输出。
4. 其他 DOCX part 保持输出文件原样，尤其不覆盖 `word/document.xml` 和 `[Content_Types].xml`。

### 6.2 风险边界

不恢复整个 `styles.xml`，原因是 UNO 另存可能同步改写 `document.xml` 中的样式引用。如果只恢复旧 styles，可能出现 styleId 或默认样式不一致。字体资产恢复只处理主题字体和字体表这类相对独立的包级资产，风险更可控。

## 7. 残留绘图治理设计

### 7.1 检测目标

需要检测输入样本文档中可能在 UNO 另存后显露的残留对象，包括：

- DrawingML group shape，例如 `wpg:wgp`
- VML shape 和 `w:pict`
- OLE embedding 和 WMF fallback
- `mc:AlternateContent` 中的兼容绘图分支
- 没有正文语义、锚在空段落上的浮动图形

### 7.2 治理策略

采用分层策略，不默认删除所有绘图：

1. **样本清理优先**：规则样本中的无关残留图形应从源 DOCX 中清理掉，保持样本干净。
2. **契约测试兜底**：对 `docs/rules/*/samples/*.docx` 增加检测，发现异常浮动绘图时失败或报告。
3. **输出后处理可选**：如后续需要对用户上传文档做自动治理，应基于明确策略删除已知污染对象，而不是泛化删除所有 drawing。

### 7.3 初始规则

针对已确认问题，可先建立样本级检测规则：

- 如果样本文档存在锚在空段落的 `wp:anchor` group shape，并且其中包含彩色箭头连接线，则判定为样本污染。
- 样本污染应在样本清理阶段删除，不应依赖运行时输出清理。

运行时输出清理只适合处理明确可识别的系统已知污染对象，例如特定样本中的 `组合 150`。对真实用户文档，不应在没有规则依据时删除用户绘图。

## 8. 测试设计

### 8.1 单元测试

为 OOXML 后处理增加纯 Python 单元测试：

- 字体资产恢复会覆盖输出 theme/fontTable/font rels/fonts。
- 字体资产恢复不会覆盖 `word/document.xml`。
- 字体资产恢复不会覆盖 `[Content_Types].xml`。
- 残留绘图检测能识别锚在空段落的彩色箭头 group shape。
- 残留绘图检测不会误报普通正文图片。

### 8.2 UNO/CLI 端到端测试

使用 Docker UNO 环境运行：

```bash
docker run --rm -v "$PWD":/workspace -w /workspace \
  thesis-review-uno-dev \
  /opt/venv/bin/python -m pytest tests/e2e/cli/test_cli_review.py -m uno -v
```

覆盖规则样本：

```text
docs/rules/table-of-contents/samples/*.docx
```

断言：

1. CLI 运行成功。
2. 输出 `marked.docx` 是合法 zip/docx。
3. 输出字体资产与输入字体资产一致。
4. 已清理样本不会在输出中出现已知残留箭头对象。
5. `issues == []` 的样本也会生成 `marked.docx` 和 `issues.json`，并通过同样的样式保真断言。

## 9. 验收标准

1. `table-of-contents-clean.docx` 输出后正文中文字体不再因主题字体改写而显示为黑体。
2. `table-of-contents-entry-first-level-spacing.docx` 清理或治理后，输出第七页不再出现无关箭头组。
3. 所有目录规则样本通过 CLI 端到端测试。
4. 宿主机纯 Python 测试通过：

```bash
uv run pytest -m "not uno" -q
```

5. Docker UNO 全量测试通过：

```bash
docker run --rm -v "$PWD":/workspace -w /workspace \
  thesis-review-uno-dev \
  /opt/venv/bin/python -m pytest -q
```

## 10. 实施顺序建议

1. 先补齐字体资产恢复测试和实现，确认字体问题修复。
2. 增加样本残留绘图检测脚本或测试，定位所有污染样本。
3. 清理已确认污染的样本文档，优先修源文件。
4. 如真实用户文档仍需要运行时治理，再设计可配置的绘图清理策略。
5. 将 `annotator.py` 中的后处理调用收敛到统一 `postprocess_marked_docx()`。

## 11. 风险与约束

- LibreOffice/UNO 对 DOCX 的保存不是字节级稳定操作，不能承诺输出包与输入包除批注外完全一致。
- 绘图对象可能是用户正文内容的一部分，运行时删除策略必须保守。
- Word/WPS/LibreOffice 对 OOXML 兼容分支的渲染差异较大，样式保真测试应尽量验证 OOXML 资产和关键对象，而不是依赖人工截图。
- 样本文档应保持干净，测试样本不应携带与规则无关的隐藏对象、OLE 嵌入或历史编辑残留。
