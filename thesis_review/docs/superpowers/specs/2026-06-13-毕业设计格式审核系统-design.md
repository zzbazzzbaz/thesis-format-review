# 毕业设计格式审核系统 — 设计文档

日期：2026-06-13
状态：待评审

## 1. 背景与目标

替代导师人工审核毕业设计论文的格式。系统接收一个 `.docx`，自动检查格式与结构问题，并把问题以**红色底纹 + 批注**的方式回写进文档，产出一个 `marked.docx` 供学生/导师查看。

本项目要**上生产环境、长期稳定运行**，因此评判标准是生产可靠性、可维护性、长期兼容性，而非一次性交付。

格式要求繁多、且无法在开发前一次梳理清楚，因此核心诉求是**规则可扩展、易维护**。架构把流程拆成三步并彻底解耦：

```text
从 Word 提取文本  →  审核文本（规则）  →  问题回写 Word
```

任何一层都能独立替换、独立测试。规则数量会持续增长，且未来会引入大模型参与语义审核，因此规则层必须做到"加一条规则成本接近零"。

### 范围（第一阶段）

- 仅支持输入 `.docx`（不支持 `.doc`、不做格式转换、不处理 PDF）
- 抽取段落与 run，以及标题/章节所需的结构信息
- 实现 6 条规则（格式 + 结构）
- 输出唯一产物 `marked.docx`（红色底纹 + 批注）
- 交付为**核心库 + CLI**，Web UI 留待后续，不在本期范围

### 非目标

- `.doc` 兼容 / `.doc` 转 `.docx`
- PDF 渲染、页面截图、跨平台渲染一致性
- AI 规则、OCR 规则的**实现**（仅在接口层为其预留位置）
- `report.json` 等结构化报告输出（已明确去掉）
- 高并发（第一阶段单实例串行，见 §2）

## 2. 关键技术决策

最关键的一个决策是**用 LibreOffice + UNO 作为 docx 读写引擎，而非 python-docx**。原因：

docx 的格式属性极少直接写在 run 上，绝大多数通过**样式继承链**（run → 段落 → 段落样式 → `basedOn` 链 → `docDefaults`）和**主题字体**（`theme1.xml`）间接决定。python-docx 的高层 API **不解析**这条继承链、也不解引用主题字体，会大面积返回 `None`，导致真实文档（尤其 WPS 的字符缩进、Office 的主题字体）大量漏检——这对生产级审核系统不可接受。

LibreOffice 不是"解析原始 XML"——它的 Writer 导入过滤器把 OOXML 读入后，会**把继承链、主题字体、样式默认值全部计算成最终生效值**，构建出内存中的文档对象模型；UNO API 读的是这个**算完之后**的模型，因此拿到的直接是"有效格式值"。把"解析正确性"这个最大风险点外包给一个被海量文档验证过的成熟引擎，是降低项目总风险的选择。

代价是引入 LibreOffice 作为部署依赖，并需处理外部进程的并发与运维——这是有标准解法的工程问题，优于自写 OOXML 解析这一持续踩坑的问题。

| 决策 | 选择 | 理由 |
|------|------|------|
| 语言 | Python | UNO 有 Python 绑定（pyuno）；AI 库生态成熟 |
| docx 读写引擎 | **LibreOffice + UNO（pyuno）** | 渲染引擎级解析，自动处理继承链/主题字体；读写同引擎，定位契约闭环 |
| 取值方式 | **UNO API 读文档对象属性** | 读已渲染的有效格式，不接触原始 XML；信息最全最准 |
| 并发模型 | **单实例 soffice 串行** | 一次解析一篇；实现最简最稳，先上线。已知吞吐上限，未来可升级实例池 |
| extractor 后端 | **直接绑定 LibreOffice** | 不做正式的可替换后端抽象；但 extractor 仅暴露 `extract()` 一个函数，换引擎只动其内部 |
| 编排 | 轻量函数管道 + 规则注册表 | 三步解耦已满足需求，不引入 LangGraph 的依赖与学习成本 |
| 规则 | 纯代码规则 | 逻辑与阈值都写在每条规则类里，复杂判断好写；改要求即改对应规则 |
| 数据模型 | pydantic | 层间契约清晰、自带校验 |
| 标注 | 红色**底纹** + 批注 | 均用 UNO 写入；UNO 支持任意颜色字符底纹（不必再退而用高亮） |
| 输出 | 仅 `marked.docx` | 去掉 reporter / report.json |
| 开发方式 | **强制 TDD** | 先写失败测试再写实现；规则层尤其受益——每条规则先写合规/违规用例 |
| 测试框架 | **pytest** | 唯一测试框架，所有测试以 pytest 运行 |

### LibreOffice/UNO 带来的连锁简化

- **不存在"绝不碰 XML"约束**：UNO 读写的是 LibreOffice 文档对象模型（已解析继承与主题），全程不接触原始 OOXML。
- **红色底纹可用**：UNO 能设任意颜色的字符底纹，标注用真正的红底纹，不必将就荧光笔高亮。
- **不依赖 python-docx**：读、写、批注全部走 UNO，项目只依赖 LibreOffice 一套。

## 3. 总体架构与模块边界

系统是一条三步管道，层间靠两个数据结构（`DocumentModel`、`Issue`）解耦：

```text
input.docx
   │
   ▼  (UNO 打开)
┌──────────────┐  产出  ┌────────────────┐
│  extractor   │ ─────▶ │ DocumentModel  │  （只读标准化文档）
│ (UNO 读属性) │        └────────────────┘
└──────────────┘                │ 只读
                                ▼
                        ┌──────────────┐  产出  ┌──────────────┐
                        │   rules      │ ─────▶ │ list[Issue]  │
                        │ (注册表循环) │        └──────────────┘
                        └──────────────┘               │ 只读
                                                        ▼
                                                ┌──────────────┐
                                                │  annotator   │ ─▶ marked.docx
                                                │ (UNO 写底纹+ │
                                                │   批注)      │
                                                └──────────────┘
```

| 模块 | 职责 | 依赖 | 不碰 |
|------|------|------|------|
| `uno_session` | 管理 soffice 进程/连接、单实例串行、打开文档 | pyuno | 不判断、不定义模型 |
| `extractor` | 用 UNO 读 → `DocumentModel` | `uno_session` | 不判断、不写文档 |
| `models` | 定义 `DocumentModel` / `Issue` / `Location` | pydantic | 无业务逻辑 |
| `rules` | 注册表 + 各规则，读 `DocumentModel` → `Issue` | 仅 `models` | 不碰 UNO/docx |
| `annotator` | 按 `Issue.location` 用 UNO 写底纹 + 批注 | `uno_session` | 不做判断 |
| `pipeline` | 串联上述步骤的一个函数 | 以上全部 | 无业务逻辑 |
| `cli` | 命令行入口 | `pipeline` | 无业务逻辑 |

**关键边界**：规则层完全不知道文档怎么来的，只看 `DocumentModel`；标注层完全不知道规则在判断什么，只看 `Issue`。extractor 与 annotator 虽都用 UNO，但通过 `DocumentModel` / `Issue` 解耦，互不依赖对方内部。

## 4. 核心数据模型

三个 pydantic 模型，是层与层之间唯一的耦合点。它们与底层引擎（LibreOffice/UNO）完全无关，未来即便换引擎也不变。

### DocumentModel（extractor 产出，rules 只读）

文档层级对应文本结构：DocumentModel（整篇）→ ParagraphBlock（段落）→ RunSpan（段落内格式连续的一段文字，UNO 中对应 text portion）。

```python
class RunSpan(BaseModel):
    id: str                       # "p-0001-r-0001"，定位用
    text: str
    run_index: int
    font_east_asian: str | None   # 中文字体（宋体/黑体），UNO: CharFontNameAsian
    font_latin: str | None        # 西文字体，UNO: CharFontName
    size_pt: float | None         # 字号（磅），UNO: CharHeight
    bold: bool                    # UNO: CharWeight
    italic: bool                  # UNO: CharPosture

class ParagraphBlock(BaseModel):
    id: str                       # "p-0001"
    text: str
    paragraph_index: int
    style_name: str | None        # 段落样式名，UNO: ParaStyleName
    outline_level: int | None     # 大纲级别：0=一级标题…None=正文，UNO: OutlineLevel
    alignment: str | None         # left/center/right/justify，UNO: ParaAdjust
    line_spacing: float | None    # 行距倍数，UNO: ParaLineSpacing
    first_line_indent_chars: float | None  # 首行缩进（字符数），由 UNO 缩进值换算
    runs: list[RunSpan]

class DocumentModel(BaseModel):
    source_docx: str
    paragraphs: list[ParagraphBlock]
```

UNO 读到的均为**有效格式**（已解析继承链与主题字体），因此这些字段不会因属性藏在样式里而漏成 `None`——这正是选 LibreOffice 的核心收益。`outline_level` 与 `style_name` 让结构规则无需解析正文文字即可判断标题层级与章节。

> 注：`line_spacing` 与 `first_line_indent_chars` 的具体换算（UNO 的 LineSpacing 结构体、缩进单位 1/100 mm → 字符数）在 extractor 内部完成，并由 extractor 测试用真实 docx 钉死。

### Issue（rules 产出，annotator 只读）

```python
class Issue(BaseModel):
    rule_id: str          # "format.body.font"
    category: str         # "format" | "structure" | "ai"
    severity: str         # "error" | "warning" | "info"
    message: str          # 给人看的说明
    expected: str | None  # "宋体"
    actual: str | None    # "楷体"
    location: Location
```

### Location（把问题定位回文档）

```python
class Location(BaseModel):
    kind: str             # "paragraph" | "run"
    block_id: str         # 段落 id
    paragraph_index: int
    run_id: str | None = None
    run_index: int | None = None
```

第一阶段仅用 `paragraph` / `run` 两种 kind；未来扩表格/图片时新增枚举值，老规则不受影响。

**定位契约（单引擎闭环）**：`paragraph_index` / `run_index` 由 extractor 按 **UNO 的段落/text-portion 枚举顺序**分配；annotator 用**同一套 UNO 枚举顺序**反查节点。读写在同一个 LibreOffice 引擎内完成，索引天然对应，不存在跨库错位风险。该契约仍用 roundtrip 测试钉死。

> **DocumentModel 是引擎无关抽象**：它描述"段落有字体、字号、行距"，不描述底层引擎怎么给值。换引擎（如未来从 UNO 换回 python-docx 或其他）只动 extractor 怎么填字段，模型与规则层不变；字段上的 UNO 属性名注释仅是 extractor 的实现提示，不属于模型契约。
>
> **字段演进路径**：第一阶段字段刻意保持精简（仅段落 + run 的基础属性），未来加规则时按需扩展，遵循 extractor 与 rules **同步演进**、annotator 不受影响的原则。已知的近期候选（不在第一阶段）：`line_spacing` 细化为 `{mode, value}` 以区分倍数/固定值；新增页面/节模型（页边距、页眉页脚、页码）以支持版式规则。UNO 模型对这些均有对应对象，地基足够，按 YAGNI 暂不实现。

## 5. 规则层与注册表

这是"扩展性"的核心：加一条规则的成本必须接近零。规则层完全不依赖 UNO/LibreOffice，只读 `DocumentModel`——这是它能高速迭代、易测试的前提。

### Rule 接口

每条规则是一个实现统一接口的对象，只做一件事：读 `DocumentModel`，返回 0 到多个 `Issue`。不碰文档引擎、不碰别的规则。

```python
class Rule(Protocol):
    rule_id: str        # "format.body.font"
    category: str       # "format" | "structure" | "ai"
    severity: str       # 默认严重级别

    def check(self, document: DocumentModel) -> list[Issue]:
        ...
```

### 一条具体规则示例

纯代码规则，逻辑与阈值都写在类里：

```python
class BodyFontRule:
    rule_id = "format.body.font"
    category = "format"
    severity = "error"
    EXPECTED_FONT = "宋体"

    def check(self, document: DocumentModel) -> list[Issue]:
        issues = []
        for para in document.paragraphs:
            if para.outline_level is not None:
                continue                      # 跳过标题，只查正文
            for run in para.runs:
                if run.font_east_asian and run.font_east_asian != self.EXPECTED_FONT:
                    issues.append(Issue(
                        rule_id=self.rule_id, category=self.category,
                        severity=self.severity,
                        message=f"正文中文字体应为{self.EXPECTED_FONT}",
                        expected=self.EXPECTED_FONT, actual=run.font_east_asian,
                        location=Location(
                            kind="run", block_id=para.id,
                            paragraph_index=para.paragraph_index,
                            run_id=run.id, run_index=run.run_index)))
        return issues
```

新增规则 = 复制骨架、改判断逻辑。

### 注册表

注册表负责"哪些规则被启用"，管道无需知道每条规则的名字：

```python
# rules/registry.py
ALL_RULES: list[Rule] = [
    BodyFontRule(), BodyFontSizeRule(), LineSpacingRule(),
    FirstLineIndentRule(), HeadingHierarchyRule(), RequiredSectionRule(),
]

def get_rules() -> list[Rule]:
    return ALL_RULES
```

管道中只需：`for rule in get_rules(): issues.extend(rule.check(document))`。

### 第一阶段规则清单（格式 + 结构）

| rule_id | 类别 | 查什么 | 阈值（通用假设） |
|---------|------|--------|------------------|
| `format.body.font` | format | 正文中文字体 | 宋体 |
| `format.body.size` | format | 正文字号 | 小四（12pt） |
| `format.body.line_spacing` | format | 正文行距 | 1.5 倍 |
| `format.body.indent` | format | 正文首行缩进 | 2 字符 |
| `structure.heading.hierarchy` | structure | 标题层级不跳级 | 一级后不可直接三级 |
| `structure.section.required` | structure | 必备章节是否齐全 | 摘要/关键词/参考文献 |

6 条覆盖段落级、run 级、结构级三类判断，足够验证架构又不过度。阈值用通用中文毕设假设，拿到真实模板后在对应规则类里调整。

### AI 规则如何"留接口"

AI 规则就是一个普通 `Rule`，只是 `check` 内部调用大模型。第一阶段不实现、不注册，但管道/注册表/Issue 都无需改动即可接入：

```python
class AbstractQualityRule:        # 第一阶段仅占位，不注册
    rule_id = "ai.abstract.quality"
    category = "ai"
    severity = "warning"
    def check(self, document: DocumentModel) -> list[Issue]:
        # 未来：拼 prompt → 调 LLM → 解析为 Issue
        return []
```

## 6. UNO 会话与并发（uno_session）

`uno_session` 是唯一管理 LibreOffice 进程与连接的模块，extractor 和 annotator 都通过它打开文档，彼此不直接持有进程。

- **单实例串行**：进程内维护一个 soffice 连接，同一时刻只处理一篇文档；并发请求排队。实现最简、最稳，先上线。
- **已知吞吐上限**：这是显式记录的权衡，不是隐藏缺陷。未来需要高并发时，升级为"实例池 + 每实例独立 user profile"，对上层（extractor/annotator）接口不变。
- **生命周期**：启动时拉起 headless soffice（`--headless --norestore`，独立 user profile），进程退出时清理；崩溃时能重启并明确报错。
- **健康检查**：启动时校验 soffice 可用、UNO 可连接，否则明确报错而非默默降级。

## 7. 标注层（Issue 回写 docx）

技术上最棘手的一层：别的层错了只是判断不准，这层错了会破坏 docx 文件。annotator 全程用 UNO，与 extractor 同引擎。

### 红色底纹 + 批注（均为 UNO 原生能力）

UNO 直接支持任意颜色的字符底纹与批注，无需手写任何 XML：

- **红色底纹**：定位到目标 text range，设其字符背景/底纹为红色（UNO 字符属性）。
  - run 级 issue → 只给该 run 对应的 text range 加底纹
  - 段落级 issue → 给整段 text range 加底纹
- **批注**：在目标 text range 上插入 Annotation（UNO 的批注对象），内容 = `Issue.message`（含 expected/actual），作者标为"审核系统"。

### annotator 流程

```text
1. 通过 uno_session 打开 input.docx（在独立副本/临时路径上操作，输入只读保留）
2. 对每个 Issue：
     按 paragraph_index / run_index，用同一套 UNO 枚举顺序定位到段落/text portion
     给目标 text range 加红色底纹
     在该位置插入批注，内容 = Issue.message
3. 用 UNO 另存为 marked.docx（保持 docx 格式）
```

### 边界与容错

- annotator 是唯一写文档的模块；规则层/AI 层一律不准碰引擎。
- 输入文件只读，所有修改在副本/临时文件上进行，最终另存为 marked.docx。
- 定位失败（索引越界、文档结构异常）不崩溃：跳过该 issue 并记日志（标记"未能标注"），其余照常处理。

## 8. 管道与 CLI

管道是把三步串起来的一个普通函数，无业务逻辑：

```python
def review(input_docx: str, output_docx: str) -> list[Issue]:
    with uno_session.open(input_docx) as doc_handle:
        document = extract(doc_handle)               # extractor（UNO 读）
    issues = []
    for rule in get_rules():                          # rules（纯 Python）
        issues.extend(rule.check(document))
    annotate(input_docx, output_docx, issues)         # annotator（UNO 写）
    return issues
```

> extract 与 annotate 各自管理自己的 UNO 文档打开/关闭；上面是示意，具体由 `uno_session` 决定是否复用同一次打开。

CLI 仅做参数解析与调用：

```text
$ thesis-review input.docx -o marked.docx
检查完成：3 处错误，1 处警告 → marked.docx
```

## 10. 测试策略

**强制 TDD，pytest 为唯一测试框架。** 每个模块遵循 红 → 绿 → 重构：先写失败测试，再写最小实现，再重构。不允许先写实现后补测试。

测试分层，各司其职：

- **extractor（兼容性看门人）**：用**真实 docx**驱动，且 **WPS 与 Microsoft Word 各存一份**同样视觉效果的 fixture，断言 UNO 抽出的字段（中文字体/字号/行距/首行缩进字符数/大纲级别）一致且正确。兼容性 bug 只在双来源真实 docx 里暴露，手构造的 Model 发现不了。
- **rules（快、透明）**：每条规则独立测，用**构造的 `DocumentModel`**（合规 + 违规两种），断言 Issue 数量与内容。构造值必须以 extractor 测试确认的真实产出为准，不凭空假设单位/语义。新增规则前先写它的合规/违规用例。
- **annotator**：标注后重新打开 marked.docx，断言目标 range 已加红底纹、批注已写入。
- **roundtrip（关键）**：钉死 §4 的定位契约——同一文档经 extractor 分配的索引，annotator 用同一套 UNO 枚举顺序必须反查到同一节点。
- **pipeline**：端到端跑一个含已知问题的 docx，断言产出 marked.docx 且问题被标注。
- **fixture + sidecar 约定**：每个真实 docx fixture 配一个同名 sidecar（`.yaml`），写明其编辑器来源与"应触发哪些 rule_id"。人工 review 核对 sidecar，测试加载时拿 sidecar 当期望值——违规点不再藏在二进制里。
- 运行方式：`pytest`（CI 环境需预装 LibreOffice）。

## 11. 错误处理

| 场景 | 处理 |
|------|------|
| 输入非 .docx / 文件不存在 | CLI 明确报错退出，不进入管道 |
| 输入是 .doc | 明确提示"仅支持 .docx"，不尝试转换 |
| LibreOffice 未安装 / UNO 连不上 | 启动健康检查时明确报错，不默默降级 |
| soffice 进程崩溃 | uno_session 重启并明确报错；不产出半成品 marked.docx |
| 某条规则内部抛异常 | 捕获并记录，跳过该规则，不影响其余规则与产物 |
| 定位失败 | 跳过该 issue 记日志，其余照常 |

## 13. 部署

**核心约束**：`uno`（pyuno）不是 pip 包，随 LibreOffice 一起安装。部署的本质是"让运行 App 的 Python 能 `import uno`"。

### 形态：单镜像（App 与 LibreOffice 同容器）

不使用 docker-compose。在已定的**单实例串行**并发模型下，App 直接以子进程拉起 headless soffice 并通过本地 socket 连 UNO，同容器最简单、最稳。docker-compose 用于编排多个独立服务，当前只有一个服务，无必要。

```dockerfile
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
    libreoffice-writer \
    python3-uno \          # 让系统 python3 能 import uno
    python3-pip \
    fonts-noto-cjk \       # 中文字体（渲染相关场景需要）
    && rm -rf /var/lib/apt/lists/*
# 用系统 python3 运行 App（与 uno 同解释器），再装项目依赖
COPY . /app
WORKDIR /app
RUN pip3 install --break-system-packages .
ENTRYPOINT ["thesis-review"]
```

### 关键坑：Python 解释器一致性

`import uno` 依赖 LibreOffice/系统提供的 Python。若用独立 venv/uv 装 pydantic，那个解释器默认 `import uno` 会失败。生产 Docker 里的解法：**统一用系统 python3 + `python3-uno`，把 pydantic 也装进同一个系统 python3**（如上 Dockerfile）。这是单镜像方案最干净的做法，避免手工拼 `PYTHONPATH` 指向 LibreOffice 的 uno 模块。

### 字体说明

UNO 读取的是文档**声明的字体名**，不要求宿主真装该字体，因此**格式审核（字体名检查）不依赖安装字体**。`fonts-noto-cjk` 仅为将来涉及真实渲染（如真分页）预留，先装无妨。

### 未来演进（非第一阶段）

需要高并发时，再升级为"LibreOffice 实例池"或把转换能力拆为独立服务（如 unoserver 模式），届时才引入 docker-compose 编排。对上层 extractor/annotator 接口不变。

## 14. 字段决策记录

第一阶段 `DocumentModel` 字段保留段落级与字符级基础属性。其中 `alignment` / `font_latin` / `bold` / `italic` 不被首期 6 条规则使用，但**予以保留**：它们是下一批必加规则（标题居中、标题黑体加粗、西文 Times New Roman）的刚需，且 extractor 在读取同一 text portion 时顺手取得、零额外成本，保留可避免近期返工。这是对"仅必要字段"原则的一个有意识的、低成本的例外。

明确**不加**的：渲染页（"第几页有什么"）——docx 不存储、依赖渲染环境、结果不稳定，违背生产稳定目标。未来若需版式规则（页边距/纸张/页眉页脚/页码），加的是稳定的"节/版式"模型（基于 UNO PageStyle + 文本节），而非渲染页。
