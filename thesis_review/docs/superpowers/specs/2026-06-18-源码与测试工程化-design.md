# 源码与测试工程化设计

日期：2026-06-18
状态：设计已确认，待实现

## 1. 背景

当前 `thesis_review/src/thesis_review/` 已经具备完整审核链路，但文件职责开始交叉：

- `models.py`、`sections.py` 是纯领域逻辑。
- `extractor.py`、`annotator.py`、`uno_session.py`、`uno_traversal.py` 是 UNO 适配层。
- `pipeline.py` 负责编排审核流程。
- `cli.py` 负责命令行入口。
- `web/` 负责 HTTP 适配。
- `rules/` 里既有运行时规则，也有 `catalog`、`case` 这类资产加载逻辑。

测试目录也处于同样状态：

- 纯单元测试、UNO 集成测试、Web 测试、规则资产测试都平铺在同一层。
- `case.yml` 已经能表达“一个 Word 样本应该命中的规则 id”，但还没有成为统一的自动化契约入口。
- Word 样本不应该再由 `tests/fixtures/` 维护第二份，样本应以 `docs/rules/*/case.yml + samples/` 为唯一来源。

本设计目标是把“源码边界”和“测试边界”都工程化，让后续规则增长、CLI 输出扩展、样本回归测试都能稳定演进。

## 2. 目标

1. 按职责重组源码目录，让每个目录只承担一种明显职责。
2. CLI 只保留输出目录模式，不保留旧的 `-o marked.docx` 兼容入口。
3. CLI 固定产出 `marked.docx` 和 `issues.json`，作为自动化和人工运行的统一结果。
4. `case.yml` 成为规则样本的唯一契约来源，用它驱动端到端规则回归测试。
5. 测试目录按类型分层，避免 unit、UNO、Web、CLI、规则契约测试混在一起。
6. 保留当前审核语义，不改变已有规则判断逻辑，只重组结构和输出边界。

## 3. 非目标

本次设计不做以下事情：

- 不新增规则逻辑。
- 不修改 `case.yml` 的基本字段语义。
- 不重新设计规则编号体系。
- 不把 Word 样本复制到 `tests/fixtures/`。
- 不保留旧 CLI 参数兼容层。
- 不引入队列、数据库、任务编排系统。

## 4. 源码目录设计

### 4.1 目标结构

建议将 `src/thesis_review/` 调整为：

```text
src/thesis_review/
  core/
    __init__.py
    models.py
    sections.py
  adapters/
    uno/
      __init__.py
      extractor.py
      annotator.py
      session.py
      traversal.py
  rules/
    __init__.py
    base.py
    context.py
    issue_factory.py
    registry.py
    toc_rules.py
    catalog/
      __init__.py
      case_loader.py
      models.py
      rule_loader.py
  engine/
    __init__.py
    review.py
    result.py
    report.py
  interfaces/
    __init__.py
    cli.py
    web/
      __init__.py
      app.py
      routes.py
      services.py
      static/
```

### 4.2 职责边界

| 目录 | 职责 |
|---|---|
| `core/` | 只放引擎无关的模型和文档分区逻辑。任何不依赖 UNO、FastAPI、CLI 的纯逻辑都应优先放这里。 |
| `adapters/uno/` | 只放 LibreOffice/UNO 读写、枚举和定位契约。这里可以知道 UNO API，但不应包含规则判断。 |
| `rules/` | 只放规则协议、规则上下文、规则检查器、规则目录和样本目录加载。这里负责“查什么”，不负责“怎么打开 Word”。 |
| `engine/` | 只负责把输入路径、规则执行、标注写回和结果序列化串起来。这里是 CLI、Web、测试共用的应用内核。 |
| `interfaces/cli.py` | 只处理命令行参数、退出码和结果展示。 |
| `interfaces/web/` | 只处理 HTTP、静态页面、上传下载和错误映射。 |

### 4.3 迁移原则

- 实现过程中可以先新增 `engine/`，再迁移调用方，但合并完成后不保留旧 `pipeline.py` 作为公共入口。
- 外部调用统一指向 `engine.review()`，CLI/Web 不再直接依赖旧 `pipeline.py`。
- 旧 `pipeline.py` 应删除，或改为内部迁移过程中的临时文件，不进入最终设计。
- `__init__.py` 只做最薄导出，不承担实现逻辑。

## 5. CLI 与输出契约

### 5.1 命令形式

CLI 只保留输出目录模式：

```bash
thesis-review review input.docx --out-dir outputs/case-a
```

不保留旧的 `-o marked.docx` 兼容入口。

### 5.2 固定产物

每次运行固定产出：

```text
outputs/case-a/
  marked.docx
  issues.json
```

不要求复制输入文件。输入 Word 的来源已经由调用方或 `case.yml` 管理。

### 5.3 `issues.json` 结构

`issues.json` 作为稳定机器读结果，至少包含以下字段：

```json
{
  "input": "path/to/input.docx",
  "marked_docx": "path/to/marked.docx",
  "summary": {
    "total": 2,
    "error": 2,
    "warning": 0,
    "info": 0
  },
  "issues": [
    {
      "rule_id": "table-of-contents-title-001",
      "severity": "error",
      "message": "目录标题文本应为“目    录”",
      "expected": "目    录",
      "actual": "目录",
      "location": {
        "target": "block",
        "block_id": "b-0003",
        "block_kind": "paragraph",
        "flow_index": 3,
        "run_id": null,
        "run_index": null
      }
    }
  ]
}
```

`issues.json` 只作为结果交换格式，不承诺 Web 展示格式不变。

## 6. 规则样本契约设计

### 6.1 唯一来源

Word 样本只允许放在：

```text
thesis_review/docs/rules/<module>/samples/*.docx
```

测试目录不再维护第二份 Word 样本库。

### 6.2 case.yml 的作用

`case.yml` 是测试样本清单和预期命中规则的正式契约，不参与生产审核。

测试读取 `case.yml` 后，对每个 case 做以下事情：

1. 定位 `file` 指向的 Word 样本。
2. 调用 CLI 生成 `marked.docx` 和 `issues.json`。
3. 只筛选当前模块的 rule id。
4. 比对 `actual_module_rule_ids == expected_rule_ids`。

### 6.3 模块过滤规则

case 只比较当前模块的规则，不要求全局规则集合完全相等。

原因是后续可能增加正文、参考文献、页眉页脚等规则；这些规则不应破坏目录模块样本的回归稳定性。

测试实现时，模块过滤应以 `rule.yml` 中当前模块的 `active` 规则为准。

### 6.4 严格性

- `expected_rule_ids` 与筛选后的 `actual_rule_ids` 必须完全相等。
- 缺失样本默认可 skip，但应在契约测试中单独报告。
- `case.yml` 中引用的规则 id 必须能在对应模块 `rule.yml` 中找到。

## 7. 测试目录设计

### 7.1 目标结构

```text
tests/
  unit/
    core/
    rules/
    engine/
    interfaces/
  integration/
    uno/
    web/
  e2e/
    cli/
  contracts/
    rules/
  support/
    model_builders.py
    rule_cases.py
  conftest.py
```

### 7.2 各层职责

| 目录 | 职责 |
|---|---|
| `unit/core/` | 纯模型、分区和小函数测试。 |
| `unit/rules/` | 规则判断逻辑的内存测试，使用 `DocumentModel` 构造助手。 |
| `unit/engine/` | `engine.review()` 的纯编排测试，可用 monkeypatch 替换适配层。 |
| `unit/interfaces/` | CLI 参数、结果格式、Web 适配层的纯 Python 测试。 |
| `integration/uno/` | 真实 UNO 环境下的 extractor、annotator、engine 级测试。 |
| `integration/web/` | Web 路由到 service 的集成测试。 |
| `e2e/cli/` | CLI 真实命令测试，验证输入目录、输出目录、`issues.json` 和 `marked.docx`。 |
| `contracts/rules/` | `case.yml` 契约测试，验证样本和规则 id 的稳定性。 |
| `support/` | 测试辅助代码，不放业务逻辑。 |

### 7.3 support 目录

`support/model_builders.py` 只负责构建内存模型，例如 `DocumentModel`、`ParagraphBlock`、`RunSpan`，用于纯规则单元测试。

它不负责生成 Word 文件，也不应与真实 `.docx` fixture 混用。

`support/rule_cases.py` 只负责加载 `case.yml`、定位样本路径、筛选模块规则 id。

## 8. 数据流

### 8.1 CLI 主流程

```text
input.docx
  → engine.review()
  → UNO 打开与抽取
  → core.DocumentModel
  → rules 检查
  → issues 列表
  → UNO 标注回写
  → marked.docx
  → issues.json
```

### 8.2 case 契约测试流程

```text
docs/rules/<module>/case.yml
  → 读取 sample.docx
  → 调用 CLI
  → 解析 issues.json
  → 过滤当前模块 active rule id
  → 与 expected_rule_ids 比对
```

### 8.3 Web 流程

Web 层只做上传、临时目录管理、调用 engine、返回下载。
它不直接承担规则判断，也不生成第二套规则结果格式。

## 9. 错误处理

### 9.1 CLI

- 输入不是 `.docx`：直接失败。
- 输入不存在：直接失败。
- 输出目录不可写：直接失败。
- `issues.json` 写入失败：直接失败。

### 9.2 case 契约

- `case.yml` 中规则 id 不存在：测试失败。
- `sample` 不存在：默认 skip，严格模式下失败。
- CLI 输出 JSON 结构不符合约定：测试失败。

### 9.3 Web

Web 层继续把用户输入错误映射为 400，把内部异常映射为 500，但 Web 不作为规则契约的唯一测试入口。

## 10. 兼容与迁移

本次明确不保留旧 CLI 参数兼容，因此迁移可以更干净：

1. 新增 `engine/` 和 `interfaces/cli.py`。
2. 把旧 `pipeline` 调用收敛到 `engine.review()`，并移除旧公共入口。
3. 将 `web/` 改为调用 `engine.review()`。
4. 将 `tests/` 拆分为 `unit/integration/e2e/contracts/support`。
5. 将规则契约测试切换为 CLI 驱动的 `case.yml` 读取方式。
6. 清理 `tests/fixtures/` 中重复的 Word 样本；测试侧不再保留 `.docx` 样本库。

## 11. 验收标准

1. `src/thesis_review/` 按职责拆分后，单个目录的职责可以用一句话说清楚。
2. CLI 只接受输出目录模式，并稳定产出 `marked.docx` 和 `issues.json`。
3. `case.yml` 能驱动规则回归测试，且按模块过滤后 `actual_rule_ids == expected_rule_ids`。
4. `tests/` 不再平铺混放所有测试类型。
5. Word 样本只保留在 `docs/rules/*/samples/`，不在 `tests/fixtures/` 重复存储。
6. 现有规则判断语义不变。

## 12. 备注

本设计与“规则体系工程化设计”互补：

- 那份 spec 解决规则资产格式和编号体系。
- 这份 spec 解决源码目录、CLI 输出和测试工程化。

两者合并后，后续新增规则模块时，应同时具备：

- `rule.yml`
- `case.yml`
- `samples/*.docx`
- CLI `issues.json`
- `contracts/rules` 回归测试
