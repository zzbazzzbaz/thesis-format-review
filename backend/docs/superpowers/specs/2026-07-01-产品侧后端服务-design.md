# 产品侧后端服务设计

日期：2026-07-01
状态：待评审

## 1. 背景与目标

`thesis_review` 已经收敛为独立、无状态的论文格式审核服务：

```http
GET /healthz
POST /api/review
```

其中 `POST /api/review` 接收 `.docx` 文件，返回 `multipart/mixed`，包含：

- `marked_docx`：标注后的 Word 文件。
- `issues_json`：结构化审核结果。

产品化后的系统采用前后端分离。前端只调用产品侧后端；产品侧后端负责用户、权限、次数、任务、历史记录、文件下载和统计；产品侧后端再通过内网 API 调用 `thesis_review` 完成真实审核。

目标：

1. 在 `backend/` 下建设 Django 产品后端。
2. 将 `thesis_review` 作为独立内网服务调用，不把用户体系、任务状态和历史记录放入 `thesis_review`。
3. 支持学生端上传 Word、查看进度、下载结果、查看历史、查看个人信息和剩余次数。
4. 支持教师端查看自己学生的上传情况、下载原文和审核结果、查看统计信息。
5. 使用 Django Admin 管理用户、角色、师生关系、次数和审核任务。

## 2. 系统边界

### 2.1 产品侧后端职责

产品侧后端负责：

- 用户登录、认证、角色与权限。
- 学生、教师、管理员身份管理。
- 学生上传原始 Word 文件。
- 学生上传次数校验与扣减。
- 审核任务创建、状态流转、失败记录。
- 后台调用 `thesis_review` 服务。
- 保存原始 Word、标注 Word、`issues.json`。
- 向前端提供任务列表、任务详情、下载接口和统计接口。
- Django Admin 管理数据。

### 2.2 `thesis_review` 服务职责

`thesis_review` 只负责：

- 接收单个 `.docx`。
- 同步执行审核。
- 返回 `marked_docx` 和 `issues_json`。
- 请求结束后清理临时文件。

`thesis_review` 不负责：

- 用户、登录、角色。
- 上传次数。
- 审核任务 ID。
- 进度状态。
- 历史记录。
- 文件长期保存。
- 教师统计。

## 3. 技术选型

后端建议使用：

- Python 3.12。
- `uv` 管理环境和依赖。
- Django。
- Django Ninja 提供前后端分离 API。
- JWT 认证，优先使用适配 Django Ninja 的轻量认证方案，避免引入 DRF 体系。
- SQLite 作为首版数据库。
- 本地文件系统作为文件存储。

轻量化约束：

- 不引入 Django REST Framework。
- 不引入 Celery。
- 不引入 Redis。
- 不引入 PostgreSQL 作为首版必需依赖。

审核过程可能较慢，不适合阻塞前端 HTTP 请求。首版采用 SQLite 数据库作为任务队列，由轻量后台 worker 管理命令轮询 `pending` 任务并调用 `thesis_review`。这能保留任务状态和历史记录，又不需要额外消息队列服务。

## 5. 角色与权限

系统角色：

| 角色 | 权限 |
|---|---|
| 学生 | 上传自己的论文，查看自己的任务、历史、下载自己的原始 Word 和结果，查看个人信息和剩余次数。 |
| 教师 | 查看绑定到自己的学生任务，下载这些学生的原始 Word 和结果，查看统计。 |
| 管理员 | 使用 Django Admin 管理所有数据。 |

权限原则：

- 学生只能访问自己的任务。
- 教师只能访问自己名下学生的任务。
- 管理员通过 Django Admin 或后台权限访问全部数据。
- 下载接口必须做对象级权限校验，不能只依赖文件路径。

## 6. 数据模型设计

### 6.1 用户与资料

使用自定义 `User`。首版建议使用自定义用户模型，避免后续扩展受限。

建议字段：

```text
User
  id
  username
  password
  name
  role: student | teacher | admin
  is_active
  is_staff
  created_at
  updated_at
```

学生资料：

```text
StudentProfile
  id
  user -> User
  student_no
  college
  major
  class_name
  teacher -> TeacherProfile
  remaining_reviews
  created_at
  updated_at
```

教师资料：

```text
TeacherProfile
  id
  user -> User
  teacher_no
  college
  title
  created_at
  updated_at
```

### 6.2 审核任务

```text
ReviewTask
  id
  student -> StudentProfile
  original_filename
  source_file
  marked_file
  issues_file
  status: pending | running | succeeded | failed
  progress
  error_message
  issue_total
  issue_error
  issue_warning
  issue_info
  submitted_at
  started_at
  finished_at
  created_at
  updated_at
```

字段说明：

- `progress` 首版可以只存 `0`、`20`、`90`、`100`，因为 `thesis_review` 无状态且不提供真实进度。
- `source_file` 保存学生上传的原始 Word。
- `marked_file` 保存 `thesis_review` 返回的标注 Word。
- `issues_file` 保存 `thesis_review` 返回的 JSON。
- 统计字段从 `issues.json.summary` 冗余写入，便于列表和教师统计查询。

### 6.3 次数扣减记录

建议单独记录次数流水，避免只修改 `remaining_reviews` 导致无法审计。

```text
ReviewQuotaLedger
  id
  student -> StudentProfile
  task -> ReviewTask
  change
  balance_after
  reason
  created_at
```

规则：

- 学生每次成功创建审核任务扣减 1 次。
- 如果任务在调用 `thesis_review` 前因为系统内部错误失败，可以考虑自动返还；如果已经进入审核流程，首版不自动返还，由管理员在 Django Admin 中手动调整。
- 扣减和任务创建必须放在数据库事务中。
- SQLite 首版使用条件扣减或应用层串行化，避免并发上传导致次数扣成负数。

## 7. 审核任务状态机

状态：

```text
pending -> running -> succeeded
pending -> running -> failed
pending -> failed
```

状态含义：

| 状态 | 含义 |
|---|---|
| `pending` | 任务已创建，等待轻量 worker 执行。 |
| `running` | 轻量 worker 已开始调用 `thesis_review`。 |
| `succeeded` | 已保存标注 Word 和 `issues.json`。 |
| `failed` | 审核失败或服务异常，记录 `error_message`。 |

前端展示：

- `pending`：等待审核。
- `running`：正在审核。
- `succeeded`：审核完成，可下载。
- `failed`：审核失败，显示简短错误。

## 8. 与 `thesis_review` 的集成

### 8.1 配置

通过环境变量配置：

```text
THESIS_REVIEW_BASE_URL=http://thesis-review:8000
THESIS_REVIEW_TIMEOUT_SECONDS=300
```

如果后续给 `thesis_review` 增加服务间认证，可增加：

```text
THESIS_REVIEW_API_KEY=...
```

### 8.2 健康检查

Django 后端可以在运维健康检查或后台诊断中调用：

```http
GET {THESIS_REVIEW_BASE_URL}/healthz
```

### 8.3 审核调用

轻量 worker 从 SQLite 中获取 `pending` 任务后调用：

```http
POST {THESIS_REVIEW_BASE_URL}/api/review
Content-Type: multipart/form-data

file=<source.docx>
```

成功响应：

```http
200 OK
Content-Type: multipart/mixed; boundary="..."
```

必须解析两个 part：

- `name="marked_docx"`，保存为任务的 `marked_file`。
- `name="issues_json"`，保存为任务的 `issues_file`，并解析 `summary` 写入任务统计字段。

失败处理：

- `400`：上传文件不符合 `thesis_review` 要求，任务置为 `failed`。
- `500`：审核服务异常，任务置为 `failed`。
- 超时或连接失败：任务置为 `failed`，记录“审核服务暂不可用”。

产品侧不要把 `thesis_review` 的内部路径、异常堆栈或原始错误直接返回给前端。

### 8.4 轻量 worker

首版不引入外部队列，使用数据库状态作为队列：

```bash
cd backend
uv run python manage.py review_worker
```

worker 行为：

1. 定时查询 `pending` 任务。
2. 使用数据库事务领取一条任务并置为 `running`。
3. 调用 `thesis_review`。
4. 保存 `marked.docx` 和 `issues.json`。
5. 从 `issues.json.summary` 写入统计字段。
6. 成功置为 `succeeded`，失败置为 `failed`。

SQLite 并发能力有限，首版只建议运行一个 `review_worker` 进程，避免多个 worker 同时争抢任务。后续如果需要多实例和高并发，再评估升级数据库和队列方案。

## 9. 文件存储策略

首版文件路径建议：

```text
media/
  reviews/
    <task_id>/
      source.docx
      marked.docx
      issues.json
```

原则：

- 上传文件保存时使用服务器生成路径，不使用用户文件名作为真实路径。
- `original_filename` 只用于展示和下载名。
- 下载必须通过 Django 视图鉴权后返回，不能直接暴露静态 media URL。
- 后续迁移对象存储时，保持 `ReviewTask` 模型字段不变，替换 storage backend。

## 11. Django Admin

Admin 需要支持：

- 管理用户。
- 管理学生资料和剩余次数。
- 管理教师资料。
- 维护师生关系。
- 查看审核任务。
- 下载任务文件。
- 查看 `issues.json` 摘要字段。
- 手动调整学生次数，并写入次数流水。

Admin 列表建议：

- `StudentProfileAdmin`：姓名、学号、专业、班级、教师、剩余次数。
- `TeacherProfileAdmin`：姓名、工号、学院、学生数量。
- `ReviewTaskAdmin`：学生、教师、原文件名、状态、错误数、警告数、提交时间、完成时间。
- `ReviewQuotaLedgerAdmin`：学生、变化值、变更后余额、原因、创建时间。

## 12. 前后端交互原则

- 前端永远不直接调用 `thesis_review`。
- 前端上传文件到 Django 后端。
- 前端通过任务详情接口轮询进度。
- 前端只使用 Django 下载接口下载文件。
- 前端不依赖 `issues.json` 文件路径；如需展示问题列表，后续可以新增结构化 JSON API。

首版不要求在线预览 Word，也不要求把 `issues.json` 展示为复杂报告页面。

## 13. 错误处理

统一错误响应：

```json
{
  "detail": "错误信息"
}
```

常见错误：

| 场景 | HTTP 状态 |
|---|---|
| 未登录 | `401` |
| 角色不允许 | `403` |
| 访问不存在或无权限任务 | `404` |
| 非 `.docx` 文件 | `400` |
| 剩余次数不足 | `400` |
| 任务未完成但下载结果 | `409` |
| 服务内部错误 | `500` |

内部错误要写日志，但前端只返回简短、安全的提示。

## 14. 并发与事务要求

学生上传时必须满足：

1. 开启数据库事务。
2. 在事务内重新读取学生资料。
3. 校验 `remaining_reviews > 0`。
4. 创建 `ReviewTask`。
5. 扣减 `remaining_reviews`。
6. 写入 `ReviewQuotaLedger`。
7. 提交事务后由 `review_worker` 轮询到该任务。

SQLite 不提供强行级锁。首版应在应用层保证同一学生上传接口串行扣减，或者使用条件更新方式扣减次数，例如只在 `remaining_reviews > 0` 时执行更新，并根据受影响行数判断是否扣减成功，确保不会扣成负数。

如果 `review_worker` 停止运行，任务会停留在 `pending`。前端应继续显示“等待审核”，运维需要重启 worker。可以增加 Admin 操作或管理命令，把长时间 `running` 的任务重置为 `pending`。

## 15. 测试策略

单元测试：

- 学生剩余次数不足时不能创建任务。
- 上传非 `.docx` 返回 400。
- 创建任务会扣减一次次数并写入流水。
- 学生不能访问其他学生任务。
- 教师不能访问非自己学生任务。
- 任务状态流转正确。
- `thesis_review` multipart 响应解析正确。

集成测试：

- mock `thesis_review` 成功响应，验证任务最终 `succeeded` 且保存三个文件。
- mock `thesis_review` 500，验证任务最终 `failed`。
- 下载接口鉴权正确。
- 教师统计字段正确。

Admin 测试：

- 管理员能查看学生资料、教师资料、审核任务和次数流水。
- 非 staff 用户不能进入 Admin。

验证命令建议：

```bash
cd backend
uv run pytest
```

## 16. 部署与配置

服务建议拆分：

```text
frontend
backend-web
backend-worker
thesis-review
```

生产环境变量：

```text
DJANGO_SECRET_KEY=...
```

`backend-web` 负责 HTTP API。

`backend-worker` 运行 `python manage.py review_worker`，负责从 SQLite 轮询并执行审核任务。

`thesis-review` 只在内网暴露，不对公网开放。

## 17. 非目标

首版不做：

- 在线编辑 Word。
- 在线预览 Word。
- 复杂报告页面。
- 真实审核进度百分比。
- 多学校、多租户。
- 支付系统。
- 自动返还所有失败任务次数。
- 前端直连 `thesis_review`。
